## Block flow and content safety

Migrations `1791495283678` and `1791626179034` create block and block-level tables; subsequent migrations extend types. `lesson-block.entity.ts`, `lesson-block-level.entity.ts` and their repositories persist ordered blocks and level content. Services validate via `BlockTypeRegistry`, lock/update revisions and manage levels. `BlockResponseDto` maps `sharedContent`, `levels`, `position` and `version`; frontend `LessonBlock` matches this and the editor reads `items`. Create/edit uses POST/PATCH and reloads the list; reorder sends complete previous and desired ID arrays; removal uses DELETE. These paths are present, not proven by a live database round trip in this audit.

All 23 catalogued types have add/edit paths in `lib/block-catalog.ts`: rich text, section intro, callout, summary, scripture passage and connection, Explore Deeper, historical evidence, image, interactive image, word and symbol study, prophecy equivalence/comparison/calculation, reflection activity, guided discovery, Continue Exploring, narrative scene, media animation, map, timeline and quiz. Corresponding backend validators are registered in `registry.ts`. Media animation supports animated WebP rather than arbitrary video; some scripture controls depend on the scripture dataset. Level visibility is separate from content variants. Rich-text conversion checks whether stored content can round-trip and locks unsupported documents; existing tests cover formatted content. The lesson editor fetches lesson, blocks, workflow and events together with `Promise.all`, so failure of any request prevents the entire workspace loading; no specific failure was observed.

Confirmed source defects addressed: the empty roles list hid integrity navigation; block views other than rich text rendered shared data even if a selected-level variant existed; visibility save could replace or discard a stored variant; a callback captured the initial selected level and could reset a selection after reload. Existing custom variants remain read-only for visibility changes because the registry currently rejects variant authoring. No data migration or content rewriting was performed.

## Verification and demonstration

Unit tests cover frontend rich-text round trips and workflow payloads, backend block services, level behavior, registry and previews. See the final response for current results. Safe end-to-end verification still needs a dedicated disposable test database and an authenticated browser; do not run backend integration or e2e scripts using the existing `.env` database. To demonstrate with an ADMIN or EDITOR on a disposable fixture: open Curriculum & Courses → a course → a lesson (or Lessons → a library lesson), select a level, choose Add content → Text, save a distinctive draft, edit it, move it, reload and compare. Use Set visibility to toggle a level without a custom variant, then preview each level. Library lessons cannot be published. Existing custom variant fixtures should show their level content and a read-only notice in visibility settings. With an ADMIN, open Publishing Integrity in the sidebar and run its read-only scan. For other existing workflows use the sidebar links Media Library, Quizzes, Assessments and Admin Accounts; course/module workflow actions and the lesson Review and Publish panel are shown according to role and server-provided status.

Test results: admin unit tests 96 passed; admin TypeScript check passed. Focused backend unit run: 8 passed, 76 failed across four files. Many service fixtures omit the newer `scriptureRefs` dependency (`stampNested` is undefined); registry expectations still describe 19 types and only rich text. These failures mean the backend block persistence and preview paths were not verified by this run.
